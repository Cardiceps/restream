# restream — ретранслятор RTMP с заглушкой (Larix → Twitch + Kick)

Написан на Rust, без внешних зависимостей.

```
Телефон (Larix) ──RTMP──▶ restream :1935 ──┐
                                            ├──▶ MediaMTX 127.0.0.1:11935 ──ffmpeg──▶ Twitch
Телефон (любой) ──SRT───▶ restream :8890 ──┘                       └─ffmpeg──▶ Kick
```

- **restream** принимает **RTMP на 1935** и **SRT на 8890** (наружу смотрит только он),
  прозрачно пересылает поток в MediaMTX и попутно читает команды завершения, которые шлёт
  телефон. RTMP и SRT ведут на один и тот же путь, поэтому их можно чередовать в одном эфире.
- **MediaMTX** слушает только `127.0.0.1:11935`, наружу не смотрит.
- **ffmpeg** на каждый включённый выход: телефон на связи → `-c copy`, телефон пропал → заглушка.

## Что изменилось по сравнению с первой версией

Раньше остановка делалась искусственно: отдельный адрес `stop/<ключ>`, который надо было
вручную включать в Larix. Теперь этого не нужно.

В RTMP **есть** команды завершения публикации — `FCUnpublish`, `deleteStream`, `closeStream`,
а в SRT — управляющий пакет `SHUTDOWN`. Larix и любой другой клиент шлют их, когда нажимаешь
Stop. MediaMTX эти команды обрабатывает, но наружу сообщает только «поток исчез», не различая
причину. Поэтому restream стоит перед MediaMTX и видит команды сам.

| Что произошло | Что видит restream | Что уходит на Twitch/Kick |
|---|---|---|
| Нажали Stop | `FCUnpublish` / `deleteStream` (RTMP) или `SHUTDOWN` (SRT) | ничего, эфир завершён |
| Пропал LTE | сокет замолчал без команд | заглушка, эфир продолжается |
| Связь вернулась | новая публикация | снова телефон |

## Про паузу

Пауза в Larix не реализована намеренно. Larix при паузе не разрывает соединение и не шлёт
служебную команду — он продолжает отправлять обычные кадры (чёрное видео с оверлеем и
тишину вместо звука). Для сервера это обычный поток, отличить его от статичной сцены нельзя.
Так что пауза работает «как есть»: зрители видят то, что показывает Larix.

## Что проверено, а что нет

Проверено на реальном MediaMTX 1.21.3 и ffmpeg 7.1 в Debian 13, по-настоящему, не на моках:

- 37 юнит-тестов (`cargo test`): разбор AMF0 и чанков RTMP, смена размера чанка, сборка
  сообщения из нескольких чтений, разбор SRT-handshake и `streamid` на реальных байтах
  libsrt, распознавание `SHUTDOWN`, разбор конфига, JSON, аргументы заглушки;
- штатный Stop по **RTMP** → `FCUnpublish` и `deleteStream` распознаны, состояние LIVE → IDLE;
- штатный Stop по **SRT** → пакет `SHUTDOWN` распознан, состояние LIVE → IDLE;
- **SRT-обрыв** (kill -9 без `SHUTDOWN`) → FALLBACK, заглушка доходит до выхода;
- переключение **RTMP → обрыв → SRT** на одном пути без перезапуска сервиса;
- обрыв без команд (в том числе «тишина в сокете» — SIGSTOP на клиенте) → FALLBACK за ~3 с;
- возврат телефона → FALLBACK → LIVE после `live_confirm_seconds`;
- `restream stop` при живом телефоне → IDLE и удержание, пока телефон не отключится;
- заглушка реально доходит до выхода: снял кадр — тёмный фон и белый текст;
- установщик целиком на чистом Debian 13, включая распределение портов.

**Не проверено**: сам Larix на телефоне, реальные Twitch и Kick, openport, QEMU на твоём
железе, SRT с реального мобильного клиента (проверял ffmpeg как источник SRT). Как именно завершает соединение конкретная версия Larix, надо посмотреть на своём
телефоне — если он просто закрывает сокет без команд, это будет выглядеть как обрыв
(ограничение самого RTMP, не программы).

## 1. Сборка

В архиве уже лежит готовый бинарник `server/restream` (x86_64). Если нужна своя сборка:

```bash
cd restream
cargo build --release
cp target/release/restream ../server/restream
```

Нужен Rust 1.66 или новее. Сеть при сборке не требуется: зависимостей нет вообще.

Проверить:

```bash
cargo test          # 27 тестов
```

## 2. Подготовка Arch

```bash
sudo pacman -S --needed qemu-base libisoburn openssh curl mpv
ls -l /dev/kvm            # должен существовать и быть доступен на запись
```

Если `/dev/kvm` нет — включи виртуализацию (Intel VT-x) в BIOS. Если нет прав:
`sudo usermod -aG kvm $USER` и перелогинься.

Распакуй архив, например, в `~/restream-kit`. Нужен SSH-ключ (`ls ~/.ssh/*.pub`;
нет — `ssh-keygen -t ed25519`).

## 3. Создать и запустить виртуалку

```bash
cd ~/restream-kit/vm
./vm.sh create     # скачает Debian 13 cloud-образ (~300 МБ), создаст диск 20 ГБ
./vm.sh start      # запуск в фоне, ждёт SSH
./vm.sh deploy     # ставит ffmpeg, MediaMTX, restream, systemd-сервисы
```

Параметры (переменные окружения): `MEM=2048 CPUS=2 DISK_SIZE=20G SSH_PORT=2222 RTMP_PORT=1935
VM_DIR=~/vm/restream`.

Сеть user-mode: ВМ сама ходит в интернет, а порт 1935 хоста проброшен в ВМ. Если на хосте
включён файрвол (ufw/nftables) — для теста с телефона по Wi-Fi открой `1935/tcp`.

В конце `deploy` напечатает адрес для Larix:

```bash
./vm.sh ssh "sudo grep '^live_path' /etc/restream/config.ini"
```

Проверка: `./vm.sh ssh restream status` — должно быть `"state": "IDLE"`.

## 4. Настройка Larix Broadcaster

**Видео:** кодек **H.264**, 1280×720, 30 fps, битрейт 2500–4000 kbps, **интервал ключевых
кадров 2 с**. **Аудио:** **AAC**, 128 kbps.
HEVC не используй: поток копируется без перекодирования, а Twitch/Kick ждут H.264.

**Одно соединение:**

| Протокол | URL |
|---|---|
| RTMP (Larix) | `rtmp://ХОСТ:1935/live/<ключ>` |
| SRT (любой клиент) | `srt://ХОСТ:8890?streamid=publish:live/<ключ>` |

Логин/пароль не нужны: защитой служит случайный ключ в пути. Автопереподключение — включить.
Второе соединение `STOP` больше не нужно. Протокол можно менять между эфирами: путь один и
тот же.

## 5. Порядок эфира

| Действие | Что происходит |
|---|---|
| Start в Larix | через 3–5 с эфир на Twitch и Kick |
| Обрыв LTE | через ~6 с заглушка, эфир не прерывается |
| Связь вернулась | через ~2 с снова телефон |
| Stop в Larix | эфир на Twitch и Kick завершён |

Ничего вручную делать не нужно: кнопка Stop в Larix и есть «закрывающий пакет».

## 6. Боевой запуск на VDS (белый IP)

Нужен Debian/Ubuntu. С домашнего компьютера:

```bash
scp -r ~/restream-kit/server user@IP_VDS:~/restream-src
ssh user@IP_VDS 'sudo bash ~/restream-src/install.sh'
```

Дальше: `sudo nano /etc/restream/config.ini`, вставить ключи Twitch/Kick, включить их
(`enabled = yes`), `sudo systemctl restart restream`.

В Larix: `rtmp://IP_VDS:1935/live/<ключ>`. Файрвол: открыть `22/tcp` и `1935/tcp`.
MediaMTX и его API наружу не смотрят вообще.

## 8. Анализ производительности

Обе версии получали одинаковый поток, одинаковые два выхода, один и тот же MediaMTX
v1.21.3. Прогоны последовательные — параллельный запуск исказил бы цифры. Три прогона
на каждый вариант, в таблицах среднее.

Стенд: Debian 13, 2 vCPU, 1,9 ГБ ОЗУ, kernel 6.1, Python 3.13.16, rustc 1.85.1,
ffmpeg 7.1.5.

Что измерялось: только процесс ретранслятора (`VmRSS` из `/proc/PID/status` и
`utime+stime` из `/proc/PID/stat`). ffmpeg у обоих вариантов одинаковый, его работа
к сравнению не относится — но чтобы понять масштаб, я замерил и её отдельно.

Замер проводился в два раунда:
- **Раунд 1** — 720p30, 3 Мбит/с, 30 секунд эфира. Хорошо показывает память.
- **Раунд 2** — 720p60, 8 Мбит/с, 45 секунд, плюс отдельный режим с 12 быстрыми
  переподключениями. Нужен для проверки нагрузки на CPU.

## Память (RSS, МБ)

| Состояние | Python | Rust | Rust + SRT |
|---|---|---|---|
| Простой (ждёт телефон) | 24,2 | **1,3** | 1,3 |
| Эфир (2 выхода) | 27,2 | **2,7** | 2,7 |
| Заглушка | 27,4 | **2,9** | 2,9 |
| Пик за прогон | 27,2 | **2,7** | 2,7 |

Разница в рабочем режиме — **10,4×**, около 24,5 МБ. В простое — **19×**: Python-версия
держит интерпретатор и модули, Rust-версия почти ничего.

CPU (процент одного ядра)

Раунд 2, тяжёлый поток 720p60 8 Мбит/с:

| Режим | Python | Rust | Разница |
|---|---|---|---|
| Эфир, 45 с | 0,639 % | **0,180 %** | 3,6× |
| 12 переподключений | 0,382 % | **0,193 %** | 2,0× |

Тики за прогон: Python 23–25, Rust 6–7.

## Потоки

| | Python | Rust | Rust + SRT |
|---|---|---|---|
| Простой | 3 | 4 | 5 |
| Эфир | 7 | 7 | 8 |

Почти одинаково. У Rust на один поток больше в простое, зато в эфире поровну.

- **Память.** Rust выигрывает в 10 раз.
- **CPU.** Rust экономнее в 2–3,6 раза.
