# restream — документация

Ретранслятор: телефон → Twitch и Kick, с заглушкой при обрыве связи.
Версия 2 на Rust: остановка определяется по штатным командам завершения, отдельного адреса
для остановки больше нет. Принимает **RTMP и SRT**.

```
Телефон ──RTMP──▶ restream :1935 ──┐
                                    ├──▶ MediaMTX 127.0.0.1:11935 ──ffmpeg──▶ Twitch
Телефон ──SRT───▶ restream :8890 ──┘                    └─ffmpeg──▶ Kick
```

Оба протокола ведут на один и тот же путь (`live/<ключ>`), поэтому в одном эфире можно
переключаться между ними: MediaMTX видит один поток, ретранслятор — одну публикацию.

## 1. Что где лежит и за что отвечает

### Архив `restream-kit` (на твоём компьютере)

| Путь | За что отвечает |
|---|---|
| `restream/` | Исходники на Rust: `Cargo.toml` и `src/`. Собирается командой `cargo build --release`. |
| `server/restream` | Готовый бинарник x86_64. Его и ставит установщик. |
| `server/install.sh` | Установщик для Debian/Ubuntu. Ставит всё нужное, создаёт конфиги и ключи, регистрирует сервисы systemd. Одинаков для VDS и для виртуалки. |
| `server/tunnel-openport.sh` | Публичный TCP-туннель (openport) для домашней виртуалки. На VDS не нужен. |
| `vm/vm.sh` | Управление тестовой виртуалкой на Arch Linux (QEMU/KVM): `create`, `start`, `deploy`, `tunnel`, `ssh`, `status`, `stop`, `destroy`. |
| `README.md` | Краткое руководство. |
| `ДОКУМЕНТАЦИЯ.md` | Этот файл. |

### Исходники (`restream/src/`)

| Файл | Что делает |
|---|---|
| `main.rs` | Разбор аргументов, `run` / `status` / `stop` / `make-fallback`, запуск всего. |
| `proxy.rs` | TCP-прокси RTMP: пересылка байт, таймаут тишины, события `publish` / `end` / `drop`. |
| `chunk.rs` | Разбор потока RTMP-чанков и вытаскивание команд. |
| `amf0.rs` | Разбор AMF0 — формата, в котором RTMP передаёт команды. |
| `relay.rs` | Машина состояний и процессы ffmpeg. |
| `config.rs` | Чтение `/etc/restream/config.ini`. |
| `http.rs` | Минимальный HTTP: клиент к API MediaMTX и сервер управления. |
| `log.rs` | Логи в stdout с меткой времени UTC. |
| `fallback.rs` | Генерация файла заглушки через ffmpeg. |
| `sys.rs` | Обработчики SIGINT/SIGTERM без внешних библиотек. |
| `srt.rs` | Приём SRT: UDP-прокси, разбор `streamid` из handshake, распознавание `SHUTDOWN`. |

Зависимостей нет: только стандартная библиотека Rust. Бинарник ~683 КБ, старт мгновенный.

### На сервере после установки (VDS или виртуалка)

| Путь | Что это |
|---|---|
| `/opt/restream/restream` | Установленный бинарник. Ссылка: `/usr/local/bin/restream` (команды `restream status`, `restream stop`, `restream make-fallback`). |
| `/usr/local/bin/mediamtx` | Медиасервер, принимает RTMP от restream. |
| `/etc/restream/config.ini` | Главный конфиг: путь-ключ, выходы Twitch/Kick, тайминги. Читается только root и сервисом, потому что там ключи стримов. |
| `/etc/mediamtx/mediamtx.yml` | Конфиг MediaMTX. Генерируется `install.sh` из `config.ini`, руками не править. |
| `/var/lib/restream/fallback.mp4` | Файл заглушки (тёмный фон с надписью «Скоро вернёмся», 720p30, H.264 + AAC). |
| `/etc/systemd/system/mediamtx.service` | Сервис приёма RTMP. |
| `/etc/systemd/system/restream.service` | Сервис ретранслятора. |
| `/etc/systemd/system/restream-tunnel.service` | Сервис туннеля (только в домашней виртуалке). |

Оба сервиса стартуют при загрузке и перезапускаются при падении. Работают от пользователя
`restream`.

### Сетевые порты

| Порт | Кто слушает | Доступ |
|---|---|---|
| `1935/tcp` | restream (прокси RTMP) | Снаружи: сюда подключается телефон по RTMP |
| `8890/udp` | restream (прокси SRT) | Снаружи: сюда подключается телефон по SRT |
| `127.0.0.1:11935` | MediaMTX (RTMP) | Только локально: сюда restream пересылает поток |
| `127.0.0.1:18890` | MediaMTX (SRT) | Только локально: сюда restream пересылает SRT-датаграммы |
| `127.0.0.1:9997` | API MediaMTX | Только локально: restream проверяет готовность потока |
| `127.0.0.1:8088` | Управляющий API restream | Только локально: команды `restream status` / `stop` |

Всё остальное в MediaMTX (RTSP, HLS, WebRTC, MoQ) выключено.

### На домашнем компьютере (Arch), папка `~/vm/restream/`

Образ Debian (qcow2), диск виртуалки `restream.qcow2`, `seed.iso` (начальная настройка
cloud-init), `qemu.pid`, `console.log`, `known_hosts`.

## 2. Принцип работы

### Зачем нужен прокси

В RTMP **есть** команды завершения публикации: `FCUnpublish`, `deleteStream`, `closeStream`.
Larix шлёт их, когда нажимаешь Stop. Это и есть тот самый «закрывающий пакет».

Проблема в том, что MediaMTX эти команды обрабатывает внутри себя, но наружу сообщает только
«поток исчез» — не различая, штатное это завершение или пропавший LTE. Поэтому restream
стоит перед MediaMTX, прозрачно пересылает байты и попутно разбирает RTMP-сообщения.

Пересылка не меняется ни на байт: клиент и MediaMTX видят друг друга как раньше.

### Что именно разбирается

restream читает поток чанков RTMP от клиента и вынимает из командных сообщений AMF0-значения.
Отслеживаются:

- `connect` — какой `app` объявил клиент;
- `publish` — на какой путь публикуется (собирается в полный путь вида `live/ключ`);
- `FCUnpublish`, `deleteStream`, `closeStream` — штатное завершение.

Обрабатывается смена размера чанка (`SetChunkSize`), заголовки чанков четырёх типов,
расширенный timestamp и склейка сообщения из нескольких чтений. Аудио и видео в память не
копируются — только пропускаются.

Разбор никогда не ломает пересылку: при любой ошибке он выключается с предупреждением в логе,
а поток продолжает идти. Единственное исключение — битый чанк, который невозможно разобрать
(например, продолжение несуществующего сообщения): тогда детект отключается совсем.

### Как это работает для SRT

В SRT тот же принцип, но другими средствами. SRT — это UDP-протокол со своим управляющим
слоем, и в нём есть настоящий «закрывающий пакет»: управляющий пакет **`SHUTDOWN`** (тип 5).
Клиент шлёт его при штатном завершении и не шлёт при обрыве. Проверено на живом трафике:
при `kill -9` пакета нет, при нормальном выходе — есть.

restream слушает UDP на 8890 и пересылает датаграммы в MediaMTX без изменений. По пути
разбирается только управляющий слой:

- **handshake** (тип 0) — из него берётся `streamid`, то есть путь публикации;
- **`SHUTDOWN`** от клиента — штатное завершение эфира.

Путь извлекается из `streamid` в одной из форм: `publish:live/ключ`, `#!::r=live/ключ,m=publish`
или просто `live/ключ`. Формат значения — 4-байтовые слова с обратным порядком байт; это
разбирается отдельно и покрыто тестом на реальных байтах libsrt.

Обрыв определяется по тишине: если от адреса нет датаграмм дольше `stall_timeout`, сессия
считается отвалившейся. При этом прокси сам отправляет `SHUTDOWN` в MediaMTX от имени
клиента — иначе тот держал бы путь занятым и не принял вернувшегося телефона.

Счётчик поколений публикации защищает от путаницы: если старая SRT-сессия «догоняет»
с запоздавшим событием обрыва уже после того, как подключилась новая, событие игнорируется.

### Три состояния

| Состояние | Что уходит на Twitch и Kick | Когда переходит дальше |
|---|---|---|
| `IDLE` | Ничего (канал офлайн) | Телефон подключился и стабильно держится `live_confirm_seconds` → `LIVE` |
| `LIVE` | Поток телефона, без перекодирования | Телефон пропал без команды завершения → сразу `FALLBACK`. Пришло завершение → `IDLE` |
| `FALLBACK` | Заглушка `fallback.mp4` по кругу | Телефон вернулся и стабилен `live_confirm_seconds` → `LIVE`. Пришло завершение → `IDLE`. Заглушка идёт дольше `fallback_max_minutes` → `IDLE` |

При каждой смене состояния все ffmpeg останавливаются и запускаются заново с новым
источником. Для Twitch и Kick это выглядит как короткое переподключение (пара секунд).

Отдельный флаг удерживает состояние после ручной команды `restream stop`: ретранслятор не
запускается заново, пока телефон хотя бы раз не отключится. Иначе живое соединение сразу
вернуло бы эфир.

### Как определяется обрыв

Два независимых признака:

1. **Команда завершения.** Разобрана `FCUnpublish` / `deleteStream` / `closeStream` (RTMP)
   или `SHUTDOWN` (SRT) — это штатный конец эфира, заглушки не будет.
2. **Тишина в сокете.** Сокет клиента не отдаёт байт дольше `stall_timeout` (по умолчанию
   6 с) и команды завершения не было — это обрыв связи, включается заглушка.

Второй признак срабатывает и когда соединение рвётся грубо, и когда оно формально живо, но
данные не идут (типично для уехавшего LTE).

### Копирование без перекодирования

Поток с телефона уходит на площадки как есть (`-c copy`), поэтому нагрузка на процессор почти
нулевая. Взамен телефон должен слать H.264 + AAC с ключевым кадром раз в 2 секунды.

### Защита

Пароля у RTMP нет, поэтому защитой служит длинный случайный ключ прямо в пути (`live/<ключ>`),
который создаёт `install.sh`. MediaMTX принимает только этот путь, на любые другие отвечает
отказом. Ключи Twitch и Kick из логов скрываются.

## 3. Сборка

Готовый бинарник лежит в `server/restream`. Если нужна своя сборка:

```bash
cd restream
cargo build --release     # бинарник в target/release/restream
cargo test                # 27 тестов
cp target/release/restream ../server/restream
```

Нужен Rust 1.66+. Сеть при сборке не нужна: внешних крейтов нет. Для другой архитектуры
(например, ARM-VDS) собери на месте или кросс-компиляцией — установщик просто берёт тот
бинарник, что лежит рядом с ним.

## 4. Запуск сразу в рабочее состояние

### Что подготовить заранее

- **Twitch**: ключ трансляции. Адрес сервера обычно `rtmp://live.twitch.tv/app`.
- **Kick**: адрес сервера и ключ из настроек стрима. Выглядит как
  `rtmps://….global-contribute.live-video.net:443/app` и ключ `sk_…`.
- **Телефон**: установленный Larix Broadcaster.

Адрес выхода в конфиге всегда пишется как «адрес сервера + `/` + ключ».

### Вариант A. VDS с белым IP (боевой)

Нужен Debian или Ubuntu и доступ по SSH с sudo.

**1. Скопировать и установить** (с домашнего компьютера, из папки с распакованным архивом):

```bash
scp -r restream-kit/server user@IP_VDS:~/restream-src
ssh user@IP_VDS 'sudo bash ~/restream-src/install.sh'
```

Установщик поставит ffmpeg и MediaMTX, создаст случайный ключ, сделает заглушку, сгенерирует
конфиг MediaMTX и запустит оба сервиса. В конце напечатает адрес для Larix.

**2. Вписать выходы.** На VDS:

```bash
sudo nano /etc/restream/config.ini
```

Приведи секции к такому виду:

```ini
[output.test]
enabled = no

[output.twitch]
enabled = yes
url = rtmp://live.twitch.tv/app/live_ТВОЙ_КЛЮЧ

[output.kick]
enabled = yes
url = rtmps://ТВОЙ_ИНГЕСТ.global-contribute.live-video.net:443/app/sk_ТВОЙ_КЛЮЧ
```

Если нужен только один сервис, второй оставь с `enabled = no`.

**3. Перезапустить и убедиться, что поднялось:**

```bash
sudo systemctl restart restream
restream status
```

Должно быть `"state": "IDLE"`: ретранслятор ждёт телефон.

**4. Открыть порт 1935.** Если включён файрвол (пример для ufw):

```bash
sudo ufw allow 22/tcp
sudo ufw allow 1935/tcp     # RTMP
sudo ufw allow 8890/udp     # SRT (если пользуешься)
```

У части хостингов порты закрываются ещё и в панели управления. Проверь там.

**5. Узнать ключ и настроить Larix:**

```bash
sudo grep '^live_path' /etc/restream/config.ini
```

В Larix:

- **Видео:** H.264, 1280×720, 30 fps, 2500–4000 kbps, ключевой кадр каждые 2 с.
- **Аудио:** AAC, 128 kbps.
- **Соединение MAIN (RTMP):** `rtmp://IP_VDS:1935/` + значение `live_path`
  (например, `rtmp://IP_VDS:1935/live/a1b2c3d4e5f6a7b8`).
- **Если нужен SRT:** укажи в клиенте `srt://IP_VDS:8890?streamid=publish:` + `live_path`
  (например, `srt://IP_VDS:8890?streamid=publish:live/a1b2c3d4e5f6a7b8`). Путь тот же самый.

HEVC не используй: поток копируется без перекодирования, а Twitch и Kick ждут H.264.

Готово. Дальше — раздел «Ежедневная работа».

### Вариант B. Домашний компьютер: виртуалка + туннель

То же самое, но вместо VDS поднимается виртуалка, а публичный адрес даёт туннель.

**1. Пакеты на Arch (один раз):**

```bash
sudo pacman -S --needed qemu-base libisoburn openssh curl
```

Нужен `/dev/kvm` (включённая виртуализация в BIOS; при нехватке прав:
`sudo usermod -aG kvm $USER` и перелогиниться) и SSH-ключ
(`ssh-keygen -t ed25519`, если его ещё нет).

**2. Создать, запустить и развернуть виртуалку:**

```bash
cd restream-kit/vm
./vm.sh create
./vm.sh start
./vm.sh deploy
./vm.sh tunnel
```

`tunnel` ставит openport как сервис с автоперезапуском и печатает публичный адрес вида
`openport.io:NNNNN`. Он проксирует порт 1935, за которым теперь стоит restream.

**3. Вписать выходы:**

```bash
./vm.sh ssh sudo nano /etc/restream/config.ini
```

Секции приводятся к тому же виду, что и в варианте A (`output.test` выключить, `output.twitch`
и `output.kick` включить и вставить адреса с ключами). Затем:

```bash
./vm.sh ssh sudo systemctl restart restream
```

**4. Узнать адрес и ключ для Larix:**

```bash
./vm.sh ssh "sudo grep '^live_path' /etc/restream/config.ini"
./vm.sh ssh "sudo journalctl -u restream-tunnel | grep -i forwarding | tail -1"
```

Вторая команда печатает строку с публичным `хост:порт`. В Larix:

`MAIN` = `rtmp://хост:порт/` + `live_path`.

Настройки видео и аудио в Larix те же, что в варианте A.

**Что нужно помнить в этом варианте:**

- Виртуалка не стартует сама при включении компьютера. После перезагрузки хоста выполни
  `./vm.sh start`: внутри неё ретранслятор и туннель поднимутся сами.
- Публичный порт openport может смениться после перезапуска туннеля или виртуалки. Тогда
  снова выполни вторую команду из шага 4 и обнови адрес в Larix.
- Исходящий канал дома должен выдерживать битрейт × число выходов (два выхода по 4 Мбит/с =
  8 Мбит/с) с запасом.
- Остановить виртуалку: `./vm.sh stop`.

### Ежедневная работа

| Действие | Как |
|---|---|
| Начать эфир | В клиенте запустить соединение MAIN (RTMP или SRT). Через 3–5 секунд пойдёт эфир на Twitch и Kick |
| Сменить протокол | Просто подключиться другим протоколом на тот же путь: RTMP и SRT взаимозаменяемы |
| Пауза | Кнопка Pause в Larix: зрители видят то, что показывает приложение |
| Потеря связи | Ничего делать не нужно: через ~6 секунд включится заглушка, при возвращении связи эфир продолжится сам |
| Закончить эфир | Нажать Stop в Larix. Ретранслятор распознает команду и снимет эфир с площадок |
| Если нужно остановить с сервера | `restream stop` |
| Если забыл закончить | Через 30 минут заглушки эфир остановится автоматически |

## 5. Справочник по конфигу `/etc/restream/config.ini`

После любого изменения: `sudo systemctl restart restream`. Если менялся
`mediamtx_read_timeout`, перед этим один раз выполни `sudo bash install.sh` из папки с
установщиком (он перегенерирует конфиг MediaMTX).

### Секция `[general]`

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `live_path` | `live/<ключ>` | Путь, на который телефон шлёт эфир |
| `fallback_file` | `/var/lib/restream/fallback.mp4` | Файл заглушки |
| `live_confirm_seconds` | 2 | Сколько секунд телефон должен быть стабилен, чтобы вернуться на него |
| `fallback_max_minutes` | 30 | Через сколько минут заглушки эфир останавливается (0 = никогда) |
| `stall_timeout` | 6.0 | Тишина в сокете (секунды), после которой это считается обрывом |
| `poll_interval` | 0.5 | Как часто ретранслятор проверяет события (секунды) |
| `listen_host`, `listen_port` | `0.0.0.0`, 1935 | Где restream принимает RTMP от телефона |
| `mediamtx_host`, `mediamtx_port` | `127.0.0.1`, 11935 | Куда пересылать поток |
| `mediamtx_rtmp` | `rtmp://127.0.0.1:11935` | Откуда ffmpeg читает поток для выходов |
| `mediamtx_api` | `http://127.0.0.1:9997` | API для проверки готовности потока (можно оставить пустым) |
| `srt_enabled` | yes | Включён ли приём SRT |
| `srt_listen_host`, `srt_listen_port` | `0.0.0.0`, 8890 | Где restream принимает SRT от телефона |
| `srt_upstream_host`, `srt_upstream_port` | `127.0.0.1`, 18890 | Куда пересылать SRT-датаграммы (SRT в MediaMTX) |
| `control_host`, `control_port` | `127.0.0.1`, 8088 | Адрес управляющего API |
| `quiet_ffmpeg` | no | `yes` — приглушить вывод ffmpeg в логи |
| `ffmpeg` | `ffmpeg` | Путь к ffmpeg |
| `mediamtx_read_timeout` | `6s` | Таймаут MediaMTX (в конфиг MediaMTX, не restream) |

### Секции `[output.ИМЯ]`

Каждая включённая секция вида `[output.…]` запускает отдельный ffmpeg. Параметры:
`enabled` (yes/no) и `url` (адрес сервера и ключ). Можно добавлять новые площадки, дописав
ещё одну секцию.

## 6. Команды для эксплуатации

```bash
restream status                      # состояние, подключён ли телефон, что с выходами
sudo ss -lunp | grep 8890            # слушается ли SRT
restream stop                        # остановить трансляцию с сервера
sudo journalctl -u restream -f       # логи ретранслятора и ffmpeg
sudo journalctl -u mediamtx -f       # логи приёма RTMP
sudo systemctl restart restream      # после правки config.ini
```

Своя заглушка (картинка или видео; звук в ней заменяется тишиной), затем перезапуск:

```bash
sudo -u restream restream make-fallback --image /путь/к/картинке.png
sudo -u restream restream make-fallback --text "Скоро вернёмся"
sudo systemctl restart restream
```

Файл должен лежать там, где его может прочитать пользователь `restream` (например, в `/tmp`).

Обновить MediaMTX: `UPDATE_MEDIAMTX=1 sudo bash install.sh` (ключи и конфиг при этом
сохраняются).

## 7. Если что-то не так

| Симптом | Что проверить |
|---|---|
| `restream status` не отвечает | `sudo systemctl status restream` и `sudo journalctl -u restream -n 50` |
| Сервис не стартует: «порт занят» | Порт 1935 занят старым MediaMTX. Проверь: `sudo ss -ltnp \| grep 1935`. В новой схеме на 1935 должен быть `restream`, а не `mediamtx` |
| Телефон не подключается | Порт 1935 открыт в файрволе и в панели VDS; в URL правильный ключ из `config.ini`; в варианте B жив ли туннель и не сменился ли порт |
| Телефон подключён, но эфира на Twitch/Kick нет | В `config.ini` стоит `enabled = yes` и правильный `url`; ошибки ffmpeg в `journalctl -u restream`; в Larix выбран H.264 и AAC |
| Эфир на Twitch есть, на Kick нет (или наоборот) | Выходы независимы: смотри строки `[ffmpeg:kick]` или `[ffmpeg:twitch]` в логах, обычно это неверный ключ или адрес |
| Заглушка включается слишком часто | Увеличь `stall_timeout` (например, до 10), проверь качество LTE и битрейт в Larix |
| SRT не подключается | Открыт ли `8890/udp` (именно UDP, не TCP); правильный ли `streamid` вида `publish:live/<ключ>`; в логе должна быть строка «SRT-публикация на …» |
| В логе «SRT отключён» | Порт 8890 занят: `sudo ss -lunp \| grep 8890`. RTMP при этом продолжает работать |
| SRT-эфир не завершается по Stop | Клиент не прислал `SHUTDOWN`. Смотри лог: строки «SRT: штатное завершение» не будет |
| Stop в Larix не завершает эфир | В логе нет строки «штатное завершение трансляции» — значит, клиент закрыл соединение без команд. Такое поведение неотличимо от обрыва |
| В логе «не удалось разобрать RTMP-поток» | Парсер сдался и детект команд отключён; поток при этом продолжает идти. Пришли лог |

## 8. Ограничения

- **Переключение «телефон ↔ заглушка» перезапускает ffmpeg**, и для площадок это короткое
  переподключение. Бесшовное переключение возможно только при постоянном перекодировании:
  это потребует отдельной доработки и больше процессора.
- **Пауза не распознаётся как отдельное состояние.** Larix при паузе продолжает слать
  обычный поток (чёрное видео и тишина), поэтому для сервера это обычная картинка.
- **Клиент без команд завершения неотличим от обрыва.** Если приложение закрывает сокет
  молча, ретранслятор включит заглушку. Это ограничение самого RTMP, а не программы.
- **RTMP и туннель не шифруются.** Защищает случайный ключ в пути. Для боя на VDS при
  желании можно включить RTMPS в MediaMTX, но Larix тогда нужен `rtmps://` и сертификат.
- **SRT-прокси работает на уровне датаграмм.** Он не буферизует и не восстанавливает потери —
  этим занимаются сами клиент и MediaMTX. Прокси только пересылает и читает управляющий слой.
- **Проверено не всё.** Реальные Larix, Twitch, Kick, openport и QEMU на твоём железе я не
  запускал, SRT проверял источником на ffmpeg, а не с телефона. Как именно завершает соединение конкретная версия Larix — надо посмотреть на
  своём телефоне в первом же тесте.
